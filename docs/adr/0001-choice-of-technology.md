# ADR-001: Вибір стратегії управління конкурентним доступом та усунення колізій при бронюванні слотів

* **Статус:** Approved
* **Дата:** 2026-10-29
* **Автор:** Студент 4 курсу спеціальності 121/F2
* **Контекст рішення:** Відповідно до вимог [SRS-FUN-02](../srs.md#2-functional-requirements) та [SRS-NFR-PERF-02](../srs.md#3-non-functional-requirements)

---

## 1. Context (Контекст та інженерна проблема)
У медичному центрі з інтенсивним онлайн-записом та паралельною роботою операторів реєстратури виникає висока конкуренція за популярні часові слоти прийому спеціалістів. 

При традиційній обробці запитів виникає стан гонитви (Race Condition): кілька користувачів одночасно бачать слот як вільний, переходять до введення персональних даних (процес триває 2–5 хвилин) і одночасно надсилають запит на підтвердження. У разі відсутності синхронізації у базі даних виникає аномалія **Double-Booking** (накладання прийомів).

Перед архітектором постала дилема: який інженерний механізм обрати для блокування слота на час заповнення даних пацієнтом без блокування всієї таблиці бази даних і без створення простоїв для інших користувачів.

---

## 2. Alternatives (Аналіз альтернатив)

### Альтернатива 1: Песимістичне блокування суто в СУБД (PostgreSQL `SELECT FOR UPDATE` на час заповнення форми)
* **Плюси:** Абсолютна транзакційна цілісність за стандартом ACID; не вимагає додаткових сервісів у стеку.
* **Мінуси:** Відкрита транзакція з блокуванням рядка тримає відкритий конект до БД протягом 3–7 хвилин, поки користувач заповнює поля на фронтенді. Це швидко вичерпує пул з'єднань PostgreSQL (Connection Exhaustion), блокує перегляд розкладу іншими клієнтами та призводить до збоїв усієї системи.

### Альтернатива 2: Оптимістичне блокування (Optimistic Locking із полем `version` у PostgreSQL)
* **Плюси:** Відсутність тривалих блокувань у БД; висока пропускна здатність на читання.
* **Мінуси:** Конфлікт виявляється лише на фінальному кроці збереження (коли версія рядка змінилася іншим користувачем). Пацієнт, витративши 5 хвилин на заповнення форми, отримує помилку «Слот вже зайнято», що критично погіршує UX і генерує надлишкові повторні запити.

### Альтернатива 3 (Обране рішення): Гібридний патерн Redis TTL Hold Slot + короткочасний `SELECT FOR UPDATE`
* **Концепція:** При кліку на слот клієнт надсилає запит на створення тимчасового ключа в Redis (`SET slot:{id}:hold patient_id EX 420 NX`). Якщо ключ успішно створено — слот вважається зарезервованим на 7 хвилин. Інші клієнти бачать статус `ON_HOLD`. На фінальному кроці бекенд перевіряє наявність ключа в Redis і відкриває атомарну транзакцію в PostgreSQL з блокуванням рядка на кілька мілісекунд суто для запису прийому.

---

## 3. Decision (Прийняте рішення)
Обрано **Альтернативу 3: Гібридний патерн Redis TTL Hold Slot + PostgreSQL `SELECT FOR UPDATE`**.

Цей вибір повністю вирішує технічне протиріччя: швидке in-memory сховище Redis бере на себе навантаження тривалого утримання слота з автоматичною інвалідацією за таймаутом (TTL), а PostgreSQL забезпечує надійне реляційне збереження медичного запису без ризику вичерпання пулу з'єднань.

---

## 4. Consequences (Інженерні компроміси та наслідки)

### Позитивні наслідки:
1. **Ліквідація Double-Booking:** Атомарна команда Redis `SET ... NX` гарантує, що лише один клієнт зможе захопити слот.
2. **Низька затримка:** Перевірка доступності та встановлення блокування відбуваються за 2–5 мс.
3. **Автоматичне звільнення:** У разі закриття вкладки пацієнтом ключ видаляється автоматично після 420 секунд без участі кронів чи фонових очищувачів.
4. **Ізоляція PostgreSQL:** Час утримання транзакційного блокування в БД скорочується до 10–20 мілісекунд (суто на час операції `INSERT INTO appointments`).

### Негативні наслідки та компроміси (Trade-offs):
1. **Ускладнення інфраструктури:** Виникає жорстка залежність від доступності інстансу Redis. У разі падіння Redis функціонал резервування слотів стає недоступним.
2. **Необхідність забезпечення високої доступності:** Для production-середовища необхідно розгортати Redis Sentinel або Redis Cluster із механізмом реплікації.
3. **Ризик розсинхронізації стану:** Потрібна додаткова логіка обробки помилок, якщо запис у Redis відбувся, а транзакція в PostgreSQL з якихось причин зазнала відкату (Rollback).
