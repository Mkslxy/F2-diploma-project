# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.1. Актуальність вибраної теми дослідження
Сучасний стан розвитку сфери охорони здоров'я характеризується стрімкою цифровою трансформацією медичних закладів та переходом від локальних облікових систем до інтегрованих цифрових екосистем. Ефективне функціонування медичного центру значною мірою визначається якістю оперативного планування робочого часу спеціалістів, раціональним розподілом кабінетного фонду та мінімізацією непродуктивних простоїв лікарів. Проте в умовах інтенсивного потоку пацієнтів традиційні інформаційні системи стикаються із суттєвими інженерними викликами, головними з яких є деградація пропускної здатності при паралельних зверненнях та ризик виникнення конфліктів доступу до часових слотів.

## 1.2. Огляд сучасних підходів до вирішення відповідних завдань в межах обраного дослідження
* **Монолітні архітектури на базі реляційних СУБД:** Використовують спільну базу даних для транзакцій і звітів. Виконання важких звітів блокує таблиці розкладу.
* **Розподілені архітектури з фоновими контурами:** Дозволяють ізолювати обчислення завантаженості персоналу у воркери Celery без затримок для HTTP API.
* **Гібридний патерн Hold Slot:** Використання швидкого Redis для тимчасового блокування слота на 7 хвилин (TTL) та PostgreSQL SELECT FOR UPDATE суто на фінальному кроці унеможливлює стан гонитви (Race Condition).

## 1.3. Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

| Критерій порівняння | Medesk | OpenEMR | Helsi | Проєкт (To-Be) |
| :--- | :--- | :--- | :--- | :--- |
| **Архітектурний підхід** | Хмарний модульний моноліт | Монолітна архітектура (LAMP) | Розподілена мікросервісна система | Розподілена система з фоновим контуром |
| **Протоколи взаємодії** | Синхронний REST (HTTPS) | Синхронний REST / SOAP | REST API, gRPC, черги подій | REST API (HTTPS), Redis протокол |
| **Керування базою даних** | PostgreSQL | MySQL | Розподілена СУБД | PostgreSQL (ACID) + Redis |
| **Керування станом клієнта** | SPA (React) | SSR (PHP) | Мікрофронтенди | Next.js App Router + RTK Query |
| **Контроль колізій слотів** | Оптимістичне блокування | Базове блокування | Черги подій | Redis Hold Slot + SELECT FOR UPDATE |
| **Аналітичний контур** | Синхронний за запитом | Синхронні SQL-звіти | Data Lake | Черги Celery + Redis |
| **Latency p95** | ~350–500 мс | ~800–1500 мс | ~200–300 мс | < 120 мс (читання), < 250 мс (запис) |

## 1.4. Аналіз обраної предметної області в межах дослідження (модель As-Is)
* **Актори:** Пацієнт, Лікар, Реєстратор, Керівник клініки.
* **Сутності:** DoctorProfile, PatientProfile, ScheduleSlot, Appointment, Office, Specialty, WorkloadReport, AuditLog.
* **Вузькі місця As-Is:**
  1. Double-Booking Race Condition при одночасному записі на той самий слот;
  2. Блокування таблиць БД важкими аналітичними запитами (деградація Latency p95 > 5000 мс, помилки HTTP 504);
  3. Надлишковий трафік HTTP Polling (150 RPS) при синхронізації статусів візитів.
* **Обмеження:** GDPR, Закон України «Про захист персональних даних», шифрування AES-256, TLS 1.3, OWASP Top 10.

## 1.5. Постановка задачі та формування вимог (модель To-Be, Core Features, NFRs)
* **SRS-FUN-01 (Автентифікація):** Авторизація на базі JWT (RS256) та рольової моделі RBAC.
* **SRS-FUN-02 (Hold Slot):** Атомарне блокування слота в Redis (TTL = 420 с).
* **SRS-FUN-03 (Бронювання):** Транзакція в PostgreSQL із SELECT FOR UPDATE.
* **SRS-FUN-04 (Життєвий цикл):** Фіксація статусів SCHEDULED -> IN_PROGRESS -> COMPLETED/CANCELLED з аудит-логом.
* **SRS-FUN-05 (Аналітика):** Фоновий розрахунок утилізації персоналу через Celery.
* **SRS-FUN-06 (Візуалізація):** Інтерактивні графіки та теплові карти кабінетів на клієнті.
* **SRS-FUN-07 (Кешування):** Клієнтський стан та інвалідація через RTK Query.
* **SRS-FUN-08 (Надійність):** Retry-пайплайн з Exponential Backoff для черг.

### Матриця NFRs
* **SRS-NFR-PERF-01:** Latency p95 <= 120 мс при 300 RPS (читання).
* **SRS-NFR-PERF-02:** Latency p95 <= 250 мс при 100 RPS (бронювання).
* **SRS-NFR-PERF-03:** Генерація звіту Celery <= 3.0 с, видача з кешу <= 50 мс.
* **SRS-NFR-SCAL-01:** Stateless Django (до 10 реплік pods).
* **SRS-NFR-SCAL-02:** Пул конектів PgBouncer до 1000 клієнтів.
* **SRS-NFR-SEC-01..03:** OAuth 2.0 / JWT RS256, TLS 1.3, AES-256, Rate Limiting 100 req/min.
* **SRS-NFR-REL-01..02:** SLA >= 99.9%, RPO <= 15 хв, RTO <= 60 хв (PostgreSQL WAL).

### Постановка задачі
Таким чином, метою кваліфікаційної роботи є проєктування та розробка розподіленої інформаційно-аналітичної системи управління медичним центром на основі клієнт-серверної архітектури з розділеними транзакційним та фоновим контурами обробки даних (Next.js, Django REST Framework, Celery, Redis, PostgreSQL) для вирішення задачі усунення колізій паралельного доступу до часових слотів спеціалістів, мінімізації транзакційних блокувань при одночасному бронюванні та автоматизації асинхронного розрахунку аналітичних показників завантаженості персоналу.

## Висновки до розділу 1
У першому розділі кваліфікаційної роботи виконано комплексний аналітичний огляд предметної області автоматизації медичних закладів та проведено порівняльний аналіз сучасних архітектурних підходів до побудови систем управління розкладом. Встановлено, що традиційні монолітні системи синхронного типу страждають на суттєву деградацію продуктивності та ризики взаємних блокувань при одночасному виконанні важких звітів і транзакцій запису.

На основі аналізу вузьких місць моделі As-Is обґрунтовано вибір розподіленої архітектури із суворим розділенням операційного та аналітичного контурів. Доведено інженерну доцільність комбінованого використання гібридного патерну тимчасового блокування слотів у пам'яті (Hold Slot на базі Redis із контролем TTL) та транзакційної фіксації запису в реляційній базі даних PostgreSQL із застосуванням песимістичного блокування SELECT FOR UPDATE, що гарантує стовідсотковий захист від стану гонитви (Race Condition) та подвійного бронювання.

Сформовано структурований інженерний контракт системи у вигляді переліку функціональних вимог (Core Features) та матриці чисельно вимірюваних нефункціональних вимог (NFRs Matrix) станом на 2026 рік із фіксацією цільових показників затримок (p95 Latency <= 120 мс при 300 RPS) та стандартів безпеки (OAuth 2.0 / JWT, AES-256, TLS 1.3). Аналітичне та практичне вирішення визначених завдань, а також деталізована інженерна реалізація зафіксованих вимог стануть предметом поглибленого опрацювання у Розділі 2 (Проєктування архітектури, баз даних та алгоритмів) та Розділі 3 (Програмна реалізація).
