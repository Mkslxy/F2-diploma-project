# Thesis Proposal / Концепція кваліфікаційного проєкту

## 1. Робоча назва проєкту (Project Title)
* **Українською:** Розробка розподіленої інформаційно-аналітичної системи управління медичним центром із модулем оптимізації та аналізу завантаженості спеціалістів
* **English:** Engineering of a Distributed Healthcare Management System with Specialist Workload Optimization and Analytics

## 2. Актуальність та проблематика (Relevance and Problem Statement)
Автоматизація процесів сучасних закладів охорони здоров'я потребує високої точності координації розкладу, мінімізації часу простою лікарів та виключення людського фактора при маршрутизації пацієнтів. Більшість існуючих рішень страждають на проблему деградації транзакційної швидкодії при генерації важких аналітичних звітів, а також на виникнення колізій паралельного доступу (конкурентні запити на бронювання однакового часового слоту).

Інженерна складність полягає у забезпеченні транзакційної консистентності записів при одночасному навантаженні, усуненні блокувань СУБД завдяки відокремленню операційного контуру від аналітичного, суворому розмежуванні прав доступу (RBAC) до чутливих медичних даних та підтримці миттєвого реактивного інтерфейсу для оперативного персоналу.

## 3. Сформована ідея продукту (Product Concept & Architecture)
Програмний комплекс є клієнт-серверною системою на базі компонентно-орієнтованого веб-клієнта (Next.js / React) та асинхронного REST API бекенда (Django REST Framework), доповненого контуром фонової обробки даних (Celery + Redis) та реляційним сховищем (PostgreSQL).

Архітектурний підхід базується на розділенні відповідальності: транзакційне ядро обробляє операційні сутності (пацієнти, лікарі, слоти розкладу) з використанням механізму песимістичних блокувань (`SELECT FOR UPDATE`), тоді як розрахунок аналітичних показників завантаженості та агрегованої звітності делегується фоновим воркерам без блокування основного HTTP-потоку.

## 4. Ключові функції системи (Core Features)
1. **Транзакційне керування розкладом із захистом від колізій (Anti Double-Booking):** механізм бронювання прийомів із блокуванням записів на рівні транзакцій СУБД для запобігання конфліктам паралельного запису.
2. **Асинхронний аналітичний контур розрахунку завантаженості:** фоновий підрахунок коефіцієнтів утилізації робочого часу лікарів, структури завантаженості за спеціальностями та динаміки скасувань через черги Celery.
3. **Рольова модель безпеки (RBAC) та журнал аудиту:** гранульоване розмежування прав доступу (Адміністратор, Лікар, Керівник) на базі JWT-токенів із логуванням операцій зміни статусів медичних записів.
4. **Реактивне керування станом та кешуванням на клієнті:** оптимізований шар збереження та інвалідації даних розкладу за допомогою Redux Toolkit та RTK Query, що зменшує кількість надлишкових мережевих запитів.
5. **Модуль управління життєвим циклом прийому:** відстеження та зміна статусів візиту (Заплановано / В процесі / Завершено / Скасовано) у реальному часі лікарем або реєстратурою.
6. **Інтерактивна аналітична панель керівника:** візуалізація метрик продуктивності клініки, теплових карт завантаженості кабінетів та звітності для прийняття управлінських рішень.
7. **Контур запобігання колізіям та ізоляції помилок черг:** автоматичне відновлення стану та механізм повторних спроб (retry policy) для фонових задач синхронізації сповіщень та аналітики.

## 5. Інструментарій та технологічний стек (Technology Stack)
* **Frontend-шар:** Next.js (App Router), TypeScript, React, Tailwind CSS.
* **Клієнтський стан та робота з API:** Redux Toolkit, RTK Query (кешування, автоінвалідація тегів запитів).
* **Backend-шар:** Python, Django, Django REST Framework (DRF).
* **Фонова обробка та черги:** Celery, Redis (Message Broker та кеш аналітичних зрізів).
* **База даних:** PostgreSQL (реляційна модель даних, індексація слотів розкладу, транзакційна цілісність).
* **Архітектурні патерни:** Layered Architecture, Repository / Service Layer, RBAC (Role-Based Access Control), Background Task Processing, Optimistic/Pessimistic Locking.
* **DevOps та якість ПЗ:** Docker, Docker Compose, GitHub Actions (CI/CD), Flake8 / Black, Pytest, Jest.

* ## 6. Порівняльний аналіз аналогів та науково-практична новизна (Competitive Analysis & Novelty)

### Порівняння з існуючими аналогами:
1. **Helsi / eHealth-інтегратори:** Фокусуються переважно на передачі звітів у державні реєстри (НСЗУ) та веденні базової електронної медичної карти (ЕМК). У них відсутній гнучкий внутрішній аналітичний інструментарій для керівника приватного медцентру щодо оптимізації завантаженості персоналу та оцінки операційного простою кабінетів.
2. **Doctor Eleks / MedWork:** Важкі монолітні Enterprise-системи клієнт-серверної архітектури минулих поколінь. Мають надмірну складність інтерфейсу, високу вартість розгортання та повільну генерацію складних аналітичних зрізів через синхронну обробку звітів на робочих станціях.
3. **Хмарні CRM для послуг (Altegio / Beauty Pro):** Легкі веб-сервіси, які не враховують медичну специфіку (нормативи часу за нозологіями, кваліфікаційні вимоги до кабінетів, взаємозв'язок процедур) та не захищені за стандартами обробки медичних персональних даних.

### Що нового пропонується у проєкті (Науково-практична новизна):
1. **Механізм тимчасового TTL-резервування слотів (Hold Slot Pattern):** використання Redis для тимчасового блокування часу (наприклад, на 7 хвилин під час вибору пацієнтом) із автоматичним поверненням у пул у разі відмови, що усуває race conditions при паралельному записі без навантаження на основну базу PostgreSQL.
2. **Асинхронний інженерний контур розрахунку коефіцієнта утилізації персоналу:** винесення ресурсомістких агрегацій завантаженості (робочі години, простої, скасовані візити) у фонові воркери Celery, що забезпечує миттєве завантаження аналітичних графіків без затримок для операційного персоналу.
3. **Модуль евристичного прогнозування та заповнення "часових вікон":** інтелектуальний аналіз розкладу спеціалістів для виявлення неефективних інтервалів (менших за стандартний прийом) та надання рекомендацій адміністраторам щодо ущільнення графіка прийомів.
