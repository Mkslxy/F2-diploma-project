# Специфікація вимог до програмного забезпечення (SRS)
## Стандарт: ISO/IEC/IEEE 29148:2018
**Проєкт:** Розподілена інформаційно-аналітична система управління медичним центром із модулем оптимізації та аналізу завантаженості спеціалістів  
**Версія:** 1.0.0-draft  
**Статус:** Approved  

---

## 1. System Context (Контекст системи та межі)
Програмна система являє собою розподілений веб-комплекс автоматизації операційного обліку та аналітики медичного центру. Система функціонує в межах захищеного периметра медичного закладу та взаємодіє з такими зовнішніми сутностями:
* **Користувачі:** Пацієнти (публічний кабінет), Лікарі (робочий кабінет фахівця), Реєстратори/Адміністратори (панель оперативного розкладу) та Керівники клініки (аналітичний дашборд).
* **Зовнішні системи (System_Ext):**
  * `SMS / Email Gateway` — сервіс відправки транзакційних повідомлень пацієнтам про статус бронювання (протокол REST / HTTPS);
  * `eHealth Integration Bus` — шлюз взаємодії з національним контуром електронної охорони здоров'я (HL7 FHIR over HTTPS);
  * `Payment Gateway (LiqPay / Fondy)` — платіжний провайдер для оплати попереднього бронювання (Webhooks / HTTPS).

## 2. Functional Requirements (Функціональні вимоги)
Усі вимоги сформульовані з використанням суворого модального дієслова «повинна»:

* **[SRS-FUN-01]** Система повинна автентифікувати користувачів за протоколом OAuth 2.0 / OIDC із генерацією криптографічно підписаних токенів JWT (RS256) та розмежовувати доступ за рольовою моделлю RBAC (пацієнт, лікар, реєстратор, керівник).
* **[SRS-FUN-02]** Система повинна реалізовувати атомарне тимчасове резервування слота розкладу (Hold Slot) в in-memory сховищі Redis із заданим часом життя ключа TTL = 420 секунд (7 хвилин).
* **[SRS-FUN-03]** Система повинна автоматично повертати зарезервований слот у статус «Вільний» (FREE) після закінчення TTL без збереження запису в базу даних.
* **[SRS-FUN-04]** Система повинна створювати фінальний запис про прийом пацієнта в СУБД PostgreSQL в межах транзакції з рівнем ізоляції Read Committed із застосуванням блокування `SELECT ... FOR UPDATE` для гарантії захисту від стану гонитви (Race Condition).
* **[SRS-FUN-05]** Система повинна керувати життєвим циклом статусу прийому за детермінованим скінченним автоматом: `SCHEDULED` -> `IN_PROGRESS` -> `COMPLETED` / `CANCELLED` із внесенням запису в аудит-журнал.
* **[SRS-FUN-06]** Система повинна делегувати розрахунок аналітичних зрізів завантаженості персоналу та простоїв кабінетів асинхронній черзі фонових задач Celery, унеможливлюючи блокування операційного HTTP-потоку.
* **[SRS-FUN-07]** Система повинна зберігати попередньо агреговані аналітичні зрізи в кеші Redis із часом інвалідації 1800 секунд та формувати інтерактивні графіки утилізації кабінетів.
* **[SRS-FUN-08]** Система повинна реалізовувати політику автоматичних повторних спроб (Exponential Backoff Retry) для фонових задач синхронізації та відправки повідомлень у разі збоїв зовнішніх API.

## 4. Verification Criteria (Критерії верифікації вимог)
* **Вимога SRS-FUN-01, SRS-NFR-SEC-01:** Верифікується набором автоматизованих тестів `pytest-django`, статичним аудитом коду в `SonarQube` (профіль Security Hotspots) та перевіркою безпеки токенів через `OWASP ZAP`.
* **Вимоги SRS-FUN-02, SRS-FUN-03, SRS-NFR-PERF-01, SRS-NFR-PERF-02:** Верифікуються запуском автоматизованого сценарію навантажувального тестування `k6` (Spike & Stress Testing: 300 RPS на читання та 100 паралельних запитів на один слот для підтвердження захисту від double-booking).
* **Вимога SRS-FUN-06, SRS-NFR-PERF-03:** Верифікується метриками черги через `Prometheus` та моніторингом воркерів у `Celery Flower`, із контролем тайм-ауту задачі.
* **Вимога SRS-NFR-SEC-02, SRS-NFR-SEC-03:** Верифікується сканером вразливостей образів контейнерів `Trivy` у CI/CD пайплайні та інтеграційними тестами валідації вхідних DTO.
* **Вимога SRS-NFR-REL-02:** Верифікується симуляцією аварійного відновлення з WAL-архіву в тестовому контурі з фіксацією таймінгу RTO/RPO.

## 5. Glossary (Глосарій термінів)
* **Hold Slot Pattern:** Патерн тимчасового резервування ресурсу в in-memory сховищі з обмеженим часом життя (TTL) для запобігання конфліктам паралельного доступу без навантаження на основну реляційну СУБД.
* **Double-Booking:** Аномалія конкурентного доступу, за якої два або більше клієнтів одночасно отримують підтвердження бронювання на однаковий часовий слот одного спеціаліста.
* **Latency (p95):** Час затримки відповіді сервера, в межах якого обробляється 95% усіх надісланих запитів до системи.
* **JWT (JSON Web Token RS256):** Компактний безпечний формат передачі клеймів між сторонами з асиметричним цифровим підписом публічним/приватним ключами за стандартом RFC 7519.
* **RBAC (Role-Based Access Control):** Метод розмежування доступу до ресурсів та ендпоінтів системи на основі призначених ролей користувачів.
* **Eventual Consistency:** Модель узгодженості даних у розподілених системах, за якої дані в аналітичних кешах стають узгодженими через певний проміжок часу після транзакції.
* **PgBouncer:** Легковажний пул з'єднань для PostgreSQL, що оптимізує навантаження на пам'ять при великій кількості одночасних клієнтських підключень.

## AI Insights (AI Disclosure)
* **Промпт аудитора ISO 29148:** Перевірка первинної чернетки SRS на атомарність вимог, наявність модальних дієслів «повинна» та виключення суб'єктивних прикметників.
* **Зауваження ШІ:** Було вказано на відсутність інструментальної верифікації для кожної вимоги (Verification Criteria) та занадто широке формулювання аналітичного модуля.
* **Внесені інженерні правки:** Додано точні інструменти перевірки (`k6`, `SonarQube`, `Trivy`, `Celery Flower`), зафіксовано унікальні індекси `SRS-FUN-xx` та `SRS-NFR-xx`, додано інженерний глосарій.
