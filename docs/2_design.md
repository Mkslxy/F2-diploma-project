### 2.8.2. Сувора бланкова специфікація критичного прецеденту UC-01

**ID та назва:** `UC-01: Тимчасове резервування слота (Hold Slot) та транзакційне створення прийому`  
**Первинний актор:** Пацієнт (або Оператор реєстратури)  
**Вторинні актори:** Redis In-Memory Store, PostgreSQL 16, SMS Gateway, Celery Task Worker  
**Короткий опис:** Забезпечує гарантований вибір та бронювання прийому без ризику колізій Double-Booking за рахунок двоетапного блокування.

* **Preconditions (Інженерні передумови):**
  * *Продуктові:* Користувач автентифікований у системі (роль `Patient` або `Registrar`), сесія активна, передано дійсний `Bearer JWT`.
  * *Інфраструктурні:* З'єднання з Redis активне (PING = PONG < 2 мс), доступний пул з'єднань PgBouncer до PostgreSQL, слот має статус `FREE`.

* **Main Success Scenario / Happy Path (Еталонний ланцюжок):**

| Крок | Дія Актора | Реакція та відповідь сервера / БД |
| :--- | :--- | :--- |
| 1. | Пацієнт обирає доступний часовий слот у розкладі та натискає «Зарезервувати». | Frontend надсилає `POST /api/v1/schedule/slots/{id}/hold`. API Gateway валідує токен та викликає `HoldSlotManager`. |
| 2. | Сервер виконує атомарне блокування. | Бекенд надсилає в Redis команду `SET slot:{id}:hold patient_id EX 420 NX`. Redis повертає `OK`. Сервер відповідає статусом `HTTP 200 OK` (TTL: 420с). |
| 3. | Клієнтський інтерфейс запускає 7-хвилинний таймер утримання слота. | На фронтенді через RTK Query статус слота оновлюється на `ON_HOLD`. Пацієнт заповнює причину візиту. |
| 4. | Пацієнт натискає «Підтвердити запис». | Frontend надсилає `POST /api/v1/appointments` із тілом запиту `{slot_id, patient_id, visit_reason}`. |
| 5. | Сервер відкриває транзакцію СУБД. | Виконується `BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED`. Виконується `SELECT * FROM schedule_slots WHERE id = slot_id FOR UPDATE`. |
| 6. | Сервер фіксує запис у БД. | Виконується `INSERT INTO appointments (..., status='SCHEDULED')`, статус слота змінюється на `BOOKED`. Додається запис до `AUDIT_LOGS`. |
| 7. | Завершення транзакції та очищення локу. | Виконується `COMMIT`. Бекенд видаляє ключ із Redis (`DEL slot:{id}:hold`) та ініціює фонову задачу Celery `recalc_workload`. |
| 8. | Пацієнт бачить вікно успішного запису. | Сервер повертає `HTTP 201 Created` із DTO створеного прийому. |

* **Postconditions (Постумови):**
  У базі даних створено новий незворотний запис у таблиці `APPOINTMENTS`, статус слота у `SCHEDULE_SLOTS` став `BOOKED`, тимчасовий ключ у Redis вилучено, ініційовано асинхронний перерахунок завантаженості персоналу.

* **Alternative Flow (AF-01A: Вибір слота, що вже зарезервований іншим користувачем):**
  * *Старт із кроку:* Крок №1 Happy Path.
  * *Умова-тригер:* Інший користувач встановив Hold на цей слот мілісекундою раніше.
  * *Обробка:* Redis повертає `nil` на операцію `SET NX`. Сервер перериває операцію, повертає клієнту `HTTP 409 Conflict` із повідомленням: «Слот щойно зарезервовано іншим пацієнтом».
  * *Повернення:* Повернення користувача на Крок №1 до таблиці вибору альтернативного вільного часу.

* **Exception Flow (EF-01A: Відмова мережі чи таймаут СУБД під час фіксації запису):**
  * *Умова-тригер:* На кроці №6 зв'язок із PostgreSQL обірвано або транзакція завершилась аварійно.
  * *Дії сервера:* Блок перехоплення помилок автоматично викликає `ROLLBACK TRANSACTION`. Запис у таблицю `APPOINTMENTS` скасовується. В аудит-лог пишеться системна помилка `DB_TIMEOUT_ROLLBACK`.
  * *Дії для клієнта:* Сервер повертає `HTTP 500 Internal Error`. Клієнт бачить повідомлення: «Виникла помилка фіксації запису. Ваш слот залишається зарезервованим за вами ще 5 хвилин, спробуйте підтвердити повторно».

## 2.9. Топологічна матриця API-маршрутів та опис потоків даних (Data Flows)

### Карта інтерфейсних маршрутів системи

| ID маршруту | HTTP метод | Топологічний шлях (URI) | Вхідний Payload / Параметри | Призначення та Контейнер-обробник |
| :--- | :--- | :--- | :--- | :--- |
| **API-REQ-01** | `POST` | `/api/v1/auth/token` | Body: `{username, password}` | Автентифікація, генерація RS256 JWT токенів (`Backend Core API`) |
| **API-REQ-02** | `GET` | `/api/v1/schedule/slots` | Query: `doctor_id, start_date, end_date` | Вибірка розкладу із клієнтським кешуванням (`Backend Core API` + Redis) |
| **API-REQ-03** | `POST` | `/api/v1/schedule/slots/{id}/hold` | Path: `id`, Body: `{patient_id}` | Встановлення тимчасового TTL-локу на 420с (`Backend Core API` $\rightarrow$ Redis) |
| **API-REQ-04** | `POST` | `/api/v1/appointments` | Body: `{slot_id, patient_id, visit_reason}` | Транзакційне бронювання прийому (`Backend Core API` $\rightarrow$ PostgreSQL) |
| **API-REQ-05** | `PATCH` | `/api/v1/appointments/{id}/status` | Path: `id`, Body: `{new_status}` | Зміна статусу візиту лікарем за FSM (`Backend Core API`) |
| **API-REQ-06** | `GET` | `/api/v1/analytics/workload` | Query: `doctor_id, period, page=1&limit=20` | Отримання розрахованої утилізації з кешу (`Backend Core API` + Celery) |

**Мережеві обмеження та інваріанти Data Flows:**
* **Обмеження розміру запитів (Max Body Size):** лімітовано 2 МБ для JSON-запитів.
* **Пагінація:** Усі спискові ендпоінти (`GET /slots`, `GET /analytics`) мають обов'язкові параметри `page` та `limit` (за замовчуванням 20, максимум 100) для запобігання Out-of-Memory.
* **CORS-політика:** Дозволено запити виключно з довіреного походження фронтенду (`https://medcenter.local`).
* **Захист від IDOR / BOLA:** Для маршрутів `/appointments/{id}` сервіс обов'язково валідує відповідність: `appointment.patient_id == request.user.id OR request.user.role IN ['Doctor', 'Registrar']`.

## 2.10. Контур безпеки програмного рішення (Application Security — AppSec)

Контур безпеки реалізовано відповідно до галузевих рекомендацій **OWASP Top 10 (2026)**:

1. **Криптографічний захист паролів:** Хешування облікових записів реалізовано на базі алгоритму **Argon2id** (пам'ять: 64 МБ, ітерації: 3, паралелізм: 4) з індивідуальною криптографічною сіллю, що унеможливлює злам через райдужні таблиці чи апаратні GPU-атаки.
2. **Захист від Mass Assignment (Broken Object Property Level Authorization):** Контролери бекенду не мають прямого доступу до моделей ORM. Усі вхідні дані проходять через суворі DTO-серіалізатори (DRF Serializers) з явно задекларованими полями для читання/запису.
3. **Захист сесій та JWT:** Access токени підписуються асиметричним ключем **RS256** із терміном життя 15 хвилин. Refresh токени зберігаються виключно в захищених cookie з прапорцями `httpOnly`, `Secure` та `SameSite=Strict`, що ліквідує загрозу викрадення через XSS.
4. **Захист від DoS / Brute-Force (Rate Limiting):** На рівні шлюзу встановлено ліміт: максимум 100 запитів на хвилину на одну IP-адресу для публічних ендпоінтів та 10 запитів на хвилину для маршруту авторизації `/api/v1/auth/token`.
5. **Журнал безпекового аудиту (Audit Logging):** Усі чутливі події (зміна статусів медичних записів, скасування візитів, спроби несанкціонованого доступу) записуються в незмінну таблицю `AUDIT_LOGS` із фіксацією `user_id`, `ip_address` та часової мітки.

## Висновки до розділу 2

У другому розділі кваліфікаційної роботи проведено повне архітектурне та логіко-алгоритмічне проєктування розподіленої системи управління медичним центром. Застосування ієрархічної методології C4 Model дозволило деталізувати систему від верхньорівневого системного контексту (Рівень 1) та контейнерної топології розгортання (Рівень 2) до покомпонентної декомпозиції критичного сервісу розкладу за принципами Clean Architecture (Рівень 3).

Розв'язання критичної проблеми колізій паралельного бронювання формалізовано через архітектурне рішення ADR-001 у форматі Майкла Нігардза, де обґрунтовано впровадження гібридного патерну тимчасового блокування слотів у пам'яті (Redis Hold Slot з TTL = 420 с) у поєднанні з транзакційним збереженням у PostgreSQL через SELECT FOR UPDATE. Шар збереження даних оптимізовано у Третій нормальній формі (3NF) із розробкою схеми індексування для забезпечення цільового часу відгуку Latency p95 <= 120 мс при навантаженні 300 RPS.

Міжсервісну взаємодію зафіксовано за принципом API-First Design у промисловому стандарті OpenAPI 3.0, а алгоритмічну логіку критичних вузлів верифіковано згідно з академічними нормами ДСТУ. Запроєктований контур безпеки AppSec на базі Argon2id, JWT RS256 та захисту від OWASP Top 10 гарантує надійність системи перед переходом до етапу безпосередньої програмної реалізації у Розділі 3.
